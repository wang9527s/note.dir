# 从零理解 AI Agent

> 面向第一次接触 Agent 的读者。读完后你应该能：说清楚 Agent 和聊天机器人到底差在哪、自己写出一个最小可用的 Agent、知道真正上线还会踩哪些坑。
>
> 全文只有一个前提：你会写一点 JavaScript / TypeScript，知道什么是 HTTP 请求。

---

## 先看一个例子

用户说："帮我修复登录页的 bug。"

一个聊天机器人的回答大概是一段文字："你可以检查 `auth.ts` 第 42 行，把 `<=` 改成 `<`。"

一个 Agent 的过程是这样：

```
用户：帮我修复登录页的 bug。

Agent 想：先看看项目结构。
  → 调用工具 list_files("src/")
  ← 返回：src/、src/auth.ts、src/login.tsx …

Agent 想：找到登录相关文件了，读一下。
  → 调用工具 read_file("src/auth.ts")
  ← 返回：文件内容（200 行）

Agent 想：token 过期判断用了 <=，应该再确认一下症状。
  → 调用工具 run_command("npm test auth")
  ← 返回：3 个测试失败，都在过期后 0ms 边界

Agent 想：确认是边界条件问题。
  → 调用工具 edit_file("src/auth.ts", ...)
  ← 返回：修改成功

Agent 想：再跑一次测试。
  → 调用工具 run_command("npm test auth")
  ← 返回：全部通过

Agent：修好了。原因是 token 过期判断的边界条件写成了 <=，已改为 < 并验证通过。
```

看完这段，你已经掌握了 Agent 的核心：

**它会自己决定下一步做什么、自己去看结果、再决定下一步——直到任务完成。**

而聊天机器人只会"说"，Agent 会"做"，并且根据做的结果调整下一步。这个"想 → 做 → 看 → 想"的循环，就是整篇文章要讲的东西。

## 第 1 章：先搞懂模型是什么

大语言模型（LLM）本质上是一个函数：

```
输入：一段文字
输出：一段文字
```

就这么简单。它有三个特点，必须刻在脑子里：

1. **无状态**。你问它两次同样的内容，它不知道上一次问过。它不记得任何人。
2. **不能执行任何东西**。它不能读文件、不能跑命令、不能上网。它只会生成文字。
3. **每次调用都是全新的**。你看到的"连续对话"，是软件每次把之前的对话重新发一遍造成的错觉。

第 3 点特别重要。所谓 AI "记住"了你说的话，实际发生的是：

```
第一次请求：[用户] 我叫小明
第二次请求：[用户] 我叫小明，[AI] 你好小明，[用户] 我叫什么？
                 ↑ 整段历史被重新发送了一遍
```

所以：**没被放进这次请求里的东西，模型就不知道。**

这也直接推导出 Agent 的第一条真理：

> **上下文窗口是 Agent 唯一的内存。**

## 第 2 章：主循环——Agent 的心脏

### 2.1 二十行代码

```ts
const messages = [{ role: 'user', content: 用户输入 }];

while (true) {
  // 1. 问模型
  const response = await callModel({ messages, tools, system: 系统提示 });

  // 2. 模型说"我说完了"
  if (response.stopReason === 'end_turn') {
    return response.text;
  }

  // 3. 模型说"我要用工具"
  if (response.stopReason === 'tool_use') {
    const results = [];
    for (const call of response.toolCalls) {
      results.push(await executeTool(call));   // ← 宿主程序执行，不是模型
    }

    messages.push(response);                          // 记下模型的意图
    messages.push({ role: 'user', content: results }); // 记下执行结果
    continue;                                          // 再想一轮
  }
}
```

所有 Agent 框架——不管叫 LangChain、AutoGPT 还是别的——底层都是这段代码。差别只在边界处理得多细。

### 2.2 第一个关键认知：模型不干活

看第 3 步的注释：`executeTool` 是**你的程序**在跑，不是模型在跑。

模型做的事只有一件：**输出一段结构化的文字，表示"我想调用 read_file，参数是 src/auth.ts"**。至于真的去读文件、读到什么，完全由你的代码决定。

理解这一点，后面所有安全、权限、沙箱的设计就都能看懂了——**模型只是建议，执行权在宿主手里**。

### 2.3 第二个关键认知：循环没有天然终点

`while (true)` 是字面意思。如果模型一直想调用工具，它就永远不停。

所以真实产品必须有停止条件：

| 情况 | 怎么办 |
| --- | --- |
| 轮数太多 | 设硬上限，比如 50 轮，到了就强制收尾 |
| token 快用光 | 压缩历史或收尾 |
| 同一件事重复做 | 识别出来，打断它 |
| 需要人拍板 | 暂停，问用户 |

> **第一课**：能跑起来只要 20 行。生产环境的工程量，90% 在判断"什么时候该停"。

### 2.4 建议现在动手

写一个只有两个工具的最小 Agent：`read_file` 和 `run_command`。让它回答"这个项目的入口文件是什么"。写下你遇到的所有问题——那些问题就是这篇文章后半部分的内容。

## 第 3 章：工具——模型的手

### 3.1 工具长什么样

一个工具包含四部分：

```ts
{
  name: 'read_file',
  description: '读取指定路径的文件内容，最多返回 2000 行',
  inputSchema: {                      // 参数长什么样
    path: 'string'
  },
  handler: async ({ path }) => {      // 宿主侧真正干活的函数
    return fs.readFile(path, 'utf8');
  }
}
```

模型看到的是前三项（名字、描述、参数格式），它据此决定"要不要用、怎么用"。第四项模型看不到，也执行不了。

### 3.2 三个新手最容易忽略的点

**第一，描述比实现更影响成功率。**

模型只能靠 `description` 判断什么时候该用这个工具。如果你写"处理文件"，模型不知道是读、写还是删。如果你写"读取文件内容，返回文本；文件不存在时报错"，它就能正确选择。

> 工具描述本质上是 prompt engineering。这是它最值钱、也最容易被糊弄的地方。

**第二，工具返回的结果也是 prompt。**

结果会原样进入下一轮的上下文。所以：

- 太长会挤占空间（返回一个 10 万行的文件，模型后面就"忘事"了）
- 太乱会误导（一堆无结构的日志，模型抓不到重点）
- 要截断、要结构化、要说清楚"还有更多，可以用参数 X 继续取"

**第三，工具不是越多越好。**

同时给模型 50 个工具，它会犹豫、会选错。常见解法是**延迟加载**：先只给一份工具目录（名字 + 一句话），模型觉得需要某个工具时再去取详情。

### 3.3 并行不是免费的

模型一次响应可以同时要求调多个工具。比如用户问"登录逻辑在哪个文件"，模型可能一次返回：

```json
[
  { "tool": "read_file", "path": "src/auth.ts" },
  { "tool": "read_file", "path": "src/login.tsx" },
  { "tool": "grep",     "pattern": "token_expired" }
]
```

这三个都是读操作，互不影响，**并行执行**能把时间从 3 秒压到 1 秒。

但如果模型一次要求：

```json
[
  { "tool": "edit_file",   "path": "src/auth.ts", "old": "expiresAt <= now", "new": "expiresAt < now" },
  { "tool": "run_command", "command": "npm test auth" }
]
```

就**不能**并行。如果测试在文件落盘前就跑了，它读到的还是旧代码，会得出"测试通过"的错误结论——顺序一换，结果就变。

再看两个写操作并行的情况：

```json
[
  { "tool": "edit_file", "path": "src/auth.ts", "old": "A", "new": "B" },
  { "tool": "edit_file", "path": "src/auth.ts", "old": "C", "new": "D" }
]
```

如果两个编辑各自基于同一份原始内容进行，后写入的会覆盖前一个的修改，A→B 白改。这叫"丢失更新"，是并行最典型的坑。

所以工具要标**批次策略**：

| 策略 | 含义 | 典型工具 |
| --- | --- | --- |
| 并行（默认） | 同批工具同时执行 | 读文件、搜索、列目录 |
| 独占 | 单独占一批，前后不并行，按模型给的顺序依次执行 | 编辑文件、写文件、执行命令 |

判断标准很简单：**这个工具执行时，会不会改变另一个工具看到的世界？** 会，就独占。

### 3.4 工具设计清单

- [ ] 一个工具只做一件事，名字用动词
- [ ] 描述里写清：做什么、什么时候用、返回什么、什么时候会失败
- [ ] 参数在宿主侧校验，不信任模型给的输入
- [ ] 错误信息要"可行动"：错在哪 + 下一步怎么做
- [ ] 输出默认截断，并说明如何取更多
- [ ] 幂等优先；不幂等的操作要确认（见下一节）

### 3.5 幂等：为什么 Agent 特别在意

**幂等**的意思是：同一个操作执行一次和执行十次，最终结果一样。Agent 特别在意这件事，因为它**天生会重试**——超时、网络抖动、模型自己重复发、循环守卫误判，都会导致同一个工具被调用多次。

举几个例子：

| 操作 | 幂等吗 | 重试两次的后果 |
| --- | --- | --- |
| `read_file("a.txt")` | 是 | 一样的内容，无影响 |
| `mkdir -p src/utils` | 是 | 第二次直接成功 |
| 删除目录下所有 `.log` | 是 | 第二次没文件可删，结果一样 |
| `edit_file` 把 "A" 替换成 "B" | 接近 | 第二次找不到 "A"，报错但不造成破坏 |
| `edit_file` 在第 10 行**插入**一行 | **否** | 插了两行，代码坏了 |
| `run_command("npm install")` | 基本是 | 第二次只是确认已安装，慢一点 |
| `run_command("git commit -m x")` | **否** | 产生两个提交（或第二次失败卡住） |
| 调外部接口发一条通知 | **否** | 用户收到两条 |

所以工具设计有三条路：

1. **尽量做成幂等**。优先表达"最终状态"，而不是"增量操作"：
   - 不幂等：`append_line("config.json", "...")`、`increment_counter()`
   - 幂等：`set_config("key", value)`、`ensure_line_present(...)`
2. **做不到幂等，就做去重**。宿主记录"这个签名已经执行过"，重试时直接返回上次结果（只对真正的重试有效，用户主动要求再来一次不能吞）。
3. **危险的不幂等操作必须人工确认**。发消息、发钱、删数据、对外发布——错了收不回来。

> 回到上一节：独占解决的是"并发顺序"问题，幂等解决的是"重复执行"问题。两个不同维度，都要管。

## 第 4 章：上下文——Agent 的记忆和舞台

### 4.1 一次请求里到底有什么

```
┌─────────────────────────────────────┐
│ 系统提示（system）                   │  你是谁、规则是什么
├─────────────────────────────────────┤
│ 静态上下文                           │  项目约定、环境信息、日期
├─────────────────────────────────────┤
│ 历史消息                             │  之前每一轮的对话和工具结果
├─────────────────────────────────────┤
│ 动态注入                             │  相关记忆、当前任务状态
├─────────────────────────────────────┤
│ 本轮用户输入                         │  ← 放最后
└─────────────────────────────────────┘
```

四块共用同一个窗口。窗口有限（比如 20 万 token，约 15 万汉字），所以每一块都要问自己：**它值这些 token 吗？**

### 4.2 位置效应：模型不是均匀阅读的

两个经验规律：

1. **头尾强、中间弱**。放在超长上下文中间的信息，模型经常"看不见"（这个现象叫 lost in the middle）。
2. **越靠后权重越高**。模型对最近的内容更敏感。

实践含义：

- 最新的指令放最后
- 长期约束在系统提示里写一次，关键节点再复述一次
- 长材料按重要性排两端，别让硬约束沉到中间

### 4.3 系统提示怎么写

系统提示不是"许愿池"（写一堆"请务必认真""非常重要"），而是一份**分层契约**：

```
第一层 · 角色与边界    你是谁，负责什么，不负责什么
第二层 · 任务说明      要做的事，输入是什么，输出是什么
第三层 · 禁区          绝对不能做的事，以及为什么
第四层 · 输出契约      格式、字段、长度、失败时怎么表达
```

四条原则：

- **具体优于强调**。写"不要编造文件路径，不确定就先列目录"，比写"绝对不要幻觉，务必准确"有效得多
- **一条约束只写一次**。同一个要求用两种说法写在两处，模型会挑宽松的那个执行
- **删掉空话**。"你可以""请注意""尽你所能"这类词不携带信息，还占空间
- **信息密度优先**。一句话能说完别写三句，能列表别写散文

### 4.4 示例（few-shot）怎么给

示例的作用不是"教"，而是**锚定输出分布**——告诉模型"我要的就是这个格式、这个颗粒度"。

- **必须包含边界情况**。只给顺利案例，模型一遇异常就自由发挥
- **3~5 条足够**。20 条同质示例只会浪费上下文
- **格式要和期望输出完全一致**。示例里多一个字段，模型就会多输出一个字段
- **正例之外给反例**。"不要像这样回答：……" 往往比正面描述更有效

### 4.5 上下文太长怎么办：压缩

循环每转一圈，消息就变长。早晚会撑爆窗口。压缩分**两大类**，先分清这个，再看具体手段：

| 类型 | 谁来压 | 典型做法 | 成本 |
| --- | --- | --- | --- |
| 确定性裁剪 | 宿主代码，**不调模型** | 超长工具结果只保留头尾，中间打省略号 | 0 次模型调用 |
| 语义摘要 | **调一次模型** | 把旧历史交给模型，生成任务状态摘要 | 1 次（或多次）模型调用 |

两者不是二选一，真实系统通常是**先裁剪、后摘要**。

#### 确定性裁剪：不花钱的第一道闸

比如"工具结果超过 5000 字符，只保留前 1600 + 后 1600 字符，中间换成 `…[truncated]…`"：

```diff
  [user] tool_result:
- ...（8000 字的构建日志）...
+ ...（前 1600 字）
+ …[已截断 4800 字，可用 read_file offset 继续读取]…
+ ...（后 1600 字）
```

规则写死在代码里，可预测、可测试、不花 token。**能靠规则解决的，别交给模型。**

#### 语义摘要：真的调模型

当裁剪也不够时，就得把旧历史交给模型生成摘要。常见三种触发时机：

| 时机 | 说明 | 代价 |
| --- | --- | --- |
| 主动摘要 | 用量到 70%~90% 就提前压 | 信息损失，但可控 |
| 超限补救 | 已经报 context 超限再救 | 多花一次调用，体验差 |
| 手动压缩 | 用户主动触发 | 可控，但打断节奏 |

**长对话还会遇到"一次压不完"的问题**：历史太长，塞不进摘要模型的窗口。这时用**分而治之**：

```
历史切成 4 段
  ↓ 每段单独摘要（并行）
摘要1 / 摘要2 / 摘要3 / 摘要4
  ↓ 再用一次调并合并
最终摘要
```

也就是 map-reduce。合并时只保留"未解决的工作、决策、约束、精确标识符"，不要把四段摘要简单拼起来——那样长度几乎没减。

**压缩是 Agent 最容易埋隐性 bug 的地方。** 摘要把关键约束弄丢后，模型行为会莫名其妙退化，而且很难排查。

#### 压缩前后长什么样

压缩前，`messages` 里可能是 40 多轮的完整记录：

```
[system]    你是 coding agent…
[user]      修复登录页 bug，不要改 public API
[assistant] 先看项目结构
[user]      (tool_result: 文件列表…)
[assistant] 读 src/auth.ts
[user]      (tool_result: 200 行源码…)
[assistant] 跑一下测试
[user]      (tool_result: 3 个失败…)
… 还有 30 多轮 …
[user]      继续
```

压缩后，前面的历史被换成一条摘要，只保留最近几轮原文：

```
[system]    你是 coding agent…              ← 不动
[user]      【历史摘要】
            目标：修复 src/auth.ts 的 token 过期边界 bug
            已完成：定位到 expiresAt <= now 应为 <，已修改；
                   已跑 npm test auth，3 个失败
            未完成：确认 3 个失败是否同一原因
            约束：不改 public API；不碰 src/legacy/
            关键位置：src/auth.ts:42
[assistant] 好的，继续排查失败的测试
[user]      (tool_result: 最近一轮工具结果…)
[user]      继续                            ← 最近几轮保持原文
```

#### 摘要用什么提示词生成

摘要本身也是一次模型调用，要用明确的模板，不能只说"总结一下"。一个能直接用的版本：

```
你负责把对话历史压缩成任务状态摘要。只返回摘要，不要寒暄。

## 绝对禁止
- 不要调用任何工具。你只有一次机会，调工具就意味着失败。
- 不要复述工具输出原文，不要列举已删除的文件内容。

## 必须保留
1. 用户最初的请求，以及当前正在做的事
2. 已完成的步骤及最终结果（改了哪些文件、命令输出了什么结论）
3. 做过的关键决定及理由
4. 未完成的事项与待解决问题
5. 用户明确提出的约束、禁止项、偏好
6. 所有标识符原样保留：文件路径、函数名、ID、URL

## 输出格式
先写 <analysis> 块梳理一遍，再写 <summary> 块给出最终摘要。
<analysis> 会被丢弃，只有 <summary> 进入上下文。

## 长度
不超过 500 字。

对话历史：
{{messages}}
```

几个设计点值得注意：

- **必须禁止调工具**。压缩调用通常只允许一轮，模型若尝试调工具，这一轮就浪费了，拿不到摘要
- **`<analysis>` + `<summary>` 两段式**。先梳理再总结，质量明显更好；梳理过程用完即弃，不占后续上下文
- **标识符原样保留**。路径和 ID 被改写或"概括"后，后续工具调用会直接失败
- **给长度上限**。不设上限时，模型倾向于把摘要写长，压缩效果打折
- **摘要通常复用主模型**。这样能命中已有 prompt 缓存，也更不容易出现格式不兼容；换更便宜的模型能省钱，但要单独验证摘要质量

#### 三条实践规则

1. **"最近 N 轮原文 + 早期摘要"** 比全部压成一段更好。模型需要近期上下文保持细节。
2. **硬约束单独存一份，压缩后重新注入**。不要指望摘要"记得住"——尤其是否定式约束（"不要改 X"），最容易在摘要里蒸发。
3. **压缩后立刻验证**。让模型复述一遍当前目标和约束，答不上来就说明摘要漏了东西。

### 4.6 推理侧：怎么让模型"想"

有时候模型不是不知道，而是"想得太快"。几个常用手段：

| 手段 | 做什么 | 什么时候用 | 成本 |
| --- | --- | --- | --- |
| 思维链（CoT） | 让它先写出中间步骤再给答案 | 多步推理、计算 | 低 |
| 扩展思考 | 模型内部想，不占最终输出 | 复杂推理 | 中（变慢） |
| ReAct | 想一步、做一步、看结果、再想 | Agent 主循环本身 | 中（多轮） |
| 先规划再执行 | 先出计划，再逐条做 | 长任务 | 中 |
| 自我反思 | 做完自查一遍，有问题重试 | 能自动判断对错的任务 | 高（至少两次调用） |
| 多采样投票 | 同一问题问多次，取多数 | 高风险决策 | 高（N 倍成本） |

**选型原则：够用就停。**

1. 一步能做完 → 直接答
2. 多步但能拆解 → CoT 或先规划
3. 需要外部反馈 → ReAct
4. 单次不可靠但**能自动验收** → 自我反思 / 投票

最后一条要强调：**只有存在自动验证信号（测试、校验、断言）时，自我反思才有意义。** 没有验证信号的自查，经常变成"越改越自信地错"。

## 第 5 章：权限——Agent 的刹车

### 5.1 为什么必须有

Agent 能删你的文件、跑任意命令、发网络请求。**它会犯错，而且有些错不可逆。**

所以执行前必须有一道关卡，**独立于模型的判断**——也就是说，不能靠模型自己说"我保证这个命令是安全的"。

### 5.2 判定流程

```
工具调用
  → 规则匹配：允许 / 拒绝 / 询问
  → 危险模式识别：rm -rf、sudo、写系统目录…
  → 路径校验：是不是越出了项目目录
  → 必要时询问用户
```

几个容易漏掉的细节：

- **权限模式本身要有开关**。一个配置写错就全放开，是最常见的事故
- **记拒绝历史**。同一个操作反复弹框，用户会直接点"全部允许"
- **沙箱和权限是两件事**。沙箱限制"能碰到什么"（文件系统、网络），权限决定"要不要问人"。两者正交，缺一不可

### 5.3 设计原则

- 默认拒绝，显式放行（fail-closed）
- 不可逆操作必须确认；可逆操作尽量自动，别烦人
- 判定要可解释：用户得知道为什么弹这个框
- 规则写进配置文件，别散落在代码里

> 一个实用判断：**如果这个操作做错了，用户要花多久恢复？** 超过一分钟的，就值得确认。

## 第 6 章：规划——对抗漂移

长任务的典型失败：跑着跑着忘了原来要干什么、重复做已完成的事、在错误方向上越走越远。

规划的作用是**把目标写下来**，让每一轮都能对照。

| 形态 | 做法 | 适用 |
| --- | --- | --- |
| 计划模式 | 先只读、出方案，人确认后再执行 | 改动大、方向不确定 |
| 任务清单 | 拆成可勾选步骤，进度可见 | 多步骤任务 |
| 计划入上下文 | 把计划注入每一轮 | 需要持续对照 |

经验：

- **规划和执行分开**。规划阶段只读不写，避免"边想边改"把方案带偏
- 计划要写成**可验证的步骤**。"跑 X 测试通过"是好计划；"优化一下代码"不是
- 每个子任务要有明确的完成信号，否则循环不知道何时退出

## 第 7 章：记忆——按作用域分三层

> 命名提醒："短期/中期/长期"没有统一定义。不同框架里，LangChain 的 short-term 指**整个会话**，CoALA 的 working memory 指**当前任务上下文**。所以下面按**作用域**命名，别名放在表里，看到别的叫法可以对着换算。

| 层 | 作用域 | 常见别名 | 实际存在哪 |
| --- | --- | --- | --- |
| 工作记忆 | 用户的**一次输入** | working memory、轮次上下文 | 本次请求的 `messages` 数组 |
| 会话记忆 | **当前会话** | short-term memory（LangChain 系） | 会话管理器保存的消息列表（超限后被摘要替换） |
| 长期记忆 | **跨会话** | long-term memory | 磁盘上的记忆文件 / 偏好库 |

### 7.1 三层分别长什么样

**工作记忆**：用户说一句话，Agent 可能为此连调好几次模型（想一步、做个工具、再想）。这几次模型调用共享的上下文，就是工作记忆——它只在"处理这一条输入"期间存在。

```
[user]      把 README 里的 Node 版本改成 22     ← 用户的这一次输入
[assistant] tool_use: read_file("README.md")
[user]      tool_result: …第 12 行写的是 Node 20…
[assistant] tool_use: edit_file(...)
[user]      tool_result: 修改成功
[assistant] 改好了                               ← 这一条输入处理完毕，工作记忆结束
```

**会话记忆**：当前会话的记忆。用户下一条消息进来时，会话管理器把之前的完整消息列表接上新消息再发。太长了就压缩（第 4.5 节的摘要），压缩后的摘要也属于会话记忆。

```
[user]      【历史摘要】用户正在升级 Node 版本，已改 README:12…
[assistant] 好的，已改完
[user]      再把 CI 配置里的也改一下        ← 新消息
```

**长期记忆**：跨会话也还在，所以必须落盘。下次会话开始时按相关性召回，注入到 prompt 里。

```
（磁盘上的记忆文件 memory/build-prefs.md）
---
name: build-prefs
description: 本仓库构建偏好
---
用 pnpm，不用 npm；Node 版本固定 22；构建前必须跑 lint。

（下次会话，召回到的内容注入 system 或 context）
[system] …已知项目约定：
         用 pnpm，不用 npm；Node 版本固定 22；构建前必须跑 lint。
```

注意长期记忆是**按相关性挑选后注入**的，不是全量塞进去——这正是下面第 1 条要点。

两个工程要点：

1. **召回质量 > 存储容量**。存得越多，越容易召回无关内容，反而污染上下文。宁少勿滥。
2. **召回想办法藏进等待时间**。模型输出是流式的，工具执行要等网络，这些时间里可以并行预取记忆，不额外增加延迟。

## 第 8 章：多 Agent——什么时候该拆

当一个上下文装不下所有事，就拆成多个 Agent。

| 机制 | 要点 |
| --- | --- |
| 子 Agent | 独立上下文，只把结论回传给主 Agent |
| 后台任务 | 不阻塞主循环，结果稍后合并 |
| 多角色协作 | 进程内通信，必须约定消息格式 |

**核心价值是上下文隔离**：主 Agent 不需要看子任务的几十万 token 中间过程，只要结论。

代价是信息在传递中丢失。所以子任务的输出格式要事先约定好——**回传什么、不回传什么**，要在设计时就定死。

新手建议：**别急着上多 Agent**。单 Agent 把上下文压缩做对，往往比拆成五个 Agent 效果更好、也更好调试。

## 第 9 章：真实世界会怎么坏

| 失败模式 | 表现 | 怎么办 |
| --- | --- | --- |
| 原地打转 | 反复执行同一个操作 | 检测重复调用，打断 |
| 结果重复 | 同样的调用得到同样的结果还在重试 | 区分"结果没变"和"结果变了" |
| 上下文腐化 | 对话越长越笨，约束被遗忘 | 压缩时保留硬约束 |
| 幻觉工具 | 调用不存在的工具，或编造参数 | 校验输入，工具说明写清楚 |
| 自我强化错误 | 自我检查后更自信地错 | 只在有自动验证信号时启用反思 |
| 无限扩张 | 任务越做越大 | 轮数上限、预算、计划边界 |

**一条通用原则，几乎所有守卫都靠它：区分「重复」与「变化」。**

- 同一操作执行两次，结果相同 → 该停
- 同一操作执行两次，结果变了 → 合法，继续

这个判断写反了，守卫就会误杀正常流程——比如"跑测试、改代码、再跑测试"看起来是重复操作，但结果不同，必须放行。

## 第 10 章：怎么知道 Agent 变好了

Agent 的输出是一条**轨迹**，不是一个答案。所以评估分两层：

**结果层**：任务完成了吗？测试通过了吗？产物对吗？

**轨迹层**：它是怎么完成的？用了几轮？调了多少次工具？有没有绕路？有没有反复？

实践要点：

- 用例集要覆盖边界和失败路径，不能只有顺利案例
- 每次只改一个变量，记录成功率 / 平均轮数 / token 消耗
- 结论要存下来，防止回退——**prompt 改坏是高频事故**，而且改坏时往往没有报错，只是悄悄变差

## 第 11 章：动手项目

### 阶段一：最小 Agent（半天）

1. 主循环 + 一个 `read_file` 工具，能回答"这个文件讲了什么"
2. 加一个 `run_command` 工具，加上确认步骤（跑命令前问用户）
3. 加轮数上限，防止死循环

做完后你会真实体会到：模型调用工具时到底返回了什么结构。

### 阶段二：让它靠谱（一两天）

4. 加历史截断，观察行为怎么退化
5. 加摘要压缩，对比压缩前后的成功率
6. 加重复调用检测

### 实验清单（比读文章有用）

1. 故意让工具返回 10 万字，看上下文什么时候撑爆、行为怎么崩
2. 同一个任务跑 5 步，记录轮数和 token 曲线
3. 把一条关键约束从系统提示中间挪到末尾，比较成功率
4. 把工具描述写含糊，观察模型选错工具的频率
5. 去掉"规划"步骤，看长任务的成功率掉多少
